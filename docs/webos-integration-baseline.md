# WebOS integration baseline

This is the independently maintained CodiServer fork. Its Git remote is the LAN box-git repository; changes suitable for the original project can be proposed separately. The browser desktop integration is not yet complete or deployed.

## Initial browser checks

On the original fork baseline `c1905c4f9df9711206866c8b39e982f52d598d88`, a local production-style build was served to Chromium. The application loaded its own `jsketcher-occ-engine` WebAssembly asset. Using the project's existing modeling test helpers, a plane was created, a rectangle drawn as a constrained sketch, and an extrusion generated a solid. Project JSON stored the plane and extrusion history; sketch JSON stored the four segments and their coincident constraints. A reload restored the history and sketch and regenerated the solid. Moving the history pointer back changed the registered model from `S:1` (extrusion) to `S:0` (plane); moving it forward regenerated `S:1`. These are narrow smoke checks, not proof of all CAD operations, geometry correctness or desktop integration.

The checked-in Cypress craft suite contains `only` selectors in `test/coreTests/testCases/craftCut.js`, so its ordinary run excludes the other cases. Remove the selectors in a temporary test copy when trying the complete suite. Its old Cypress/Electron runner is being investigated; do not report a full-suite pass without a completed run.

## Desktop integration still required

Project and sketch data currently use browser `localStorage`, and the app's built-in file and project interface needs to be connected to the signed-in desktop file service with account isolation. Resource paths, external requests, cleanup, touch, accessibility, embedding policy, and larger models also need review. Preserve independent windows and each window's modeling state. Do not commit installed dependencies or generated build output.

The experimental `?DEFAULT&webos=1` mode gives each CAD window a separate in-memory project-storage service; closing or reloading loses its contents. A local Chrome test checks the storage service's isolation between two windows, reset on reload and preservation of ordinary standalone `localStorage`. It does not exercise an entire modeling workflow, other browser storage, direct standalone Sketcher windows, or account authorization. This mode does not yet connect to My files and is not integrated into the desktop. Do not use it to claim persistence or multi-account security. The full host bridge must cover project history and sketches together, unsaved sketches, conflict handling and independent window cleanup before release.

`projectManager.snapshotCurrentProject()` produces the upstream model-and-sketch bundle from the current workspace, without saving a desktop file. It refuses to snapshot an open in-place sketch, an active operation, or a rewound history pointer, since the existing project format reloads the end of history. A local Chromium test using real modeling helpers created a plane, rectangle sketch and extrusion, checked these refusal paths, and restored the bundle in another temporary window with matching history and sketch data. Desktop and emulated-phone viewport runs passed; this is not a physical touch test, account storage bridge, authorization mechanism, general import validator, or proof for every modeling operation. Save during other asynchronous operations and malformed bundles need further review.

`restoreSnapshotInEmptyWorkspace(json)` is an experimental host primitive for a fresh `webos=1` window. It checks JSON size and basic bundle shape, known operation IDs and unique sketch IDs before staging, rejects an occupied workspace, and waits for the craft pipeline. Assembly constraints and custom workbenches are rejected on snapshot and restore until those can be verified; otherwise upstream may silently skip unsupported constraints. A failure after staging marks the workspace uncertain; the host must discard it, not show it as a valid project. The host must also keep the window hidden and prevent interaction until restore succeeds. Local desktop and emulated-phone modeling tests restore a real extrusion and check malformed JSON, duplicate sketches, unknown operations, unsupported assembly/workbench data, existing-workspace refusal and an injected synchronous loader failure. These checks do not validate all operation parameters, sketch geometry or hostile input, nor do they cover every asynchronous failure or make this a secure import boundary. The My files transport, account/session checks and actual host lifecycle are not implemented.

In `webos=1`, the File menu's Open, Save and Save As actions now send same-origin `codiJSketcher` file-action requests to the embedding parent; they do not themselves read or save a file. The host must validate message origin and source frame, handle the signed-in account and file-version checks, and report completion or failure. A top-level temporary window has no parent file service and refuses these actions. The embedded File menu and quick toolbar omit standalone project-management and local STL/PNG downloads until they have desktop file handling. Other export routes, including contextual DXF, still need review. Local desktop and emulated-phone tests check the three requests, menu configuration and unchanged standalone Save behavior; no real desktop host or physical touch was tested.

The embedded `index-webos.html` avoids external font requests and supplies a full-height canvas. Webpack infers its asset base from the bundle URL so it can be served below a desktop asset path. A local nested-path test loaded the CAD engine without external requests; desktop and emulated-phone model tests created and restored a real extrusion at that path. An initial embedded page without a full-height root produced a zero-sized sketch and failed extrusion; adding the height fixed the tested case. Other viewport sizes and real touch remain open. The build now fails when webpack reports compilation errors instead of silently continuing; a focused test covers both compiler errors and success.

The embedded mode uses a bounded arithmetic parser for project expressions, sketch constants and numeric tool input instead of executing those values as JavaScript. It accepts numerical variables, arithmetic and a limited set of `Math` constants and functions; unsupported JavaScript is rejected on project restore and snapshot. The JavaScript debugger and separate sketch-tab action are unavailable in this mode. The standalone upstream mode retains its existing behavior. The embedded parser has unit tests for arithmetic and code-injection attempts; a real modeling test checks calculated variables, rejection of hostile project expressions and restore. Vendored verb.js startup no longer uses `new Function`, and rejects string timer handlers. Under the actual desktop Content Security Policy, the next startup blocker is `numeric` 1.2.6, which dynamically generates functions; it has not been fixed. Full compatibility, every route capable of running code, and secure handling of untrusted CAD files remain under review. Do not deploy this app or relax the site's security policy based on these limited tests.

The bundled `jsketcher-occ-engine` is a separate WebAssembly dependency. The package version references commit `5efaf53accb45bac475155fc4d5552642c19e91e` in `Autodrop3d/occt-interpreter`; that repository identifies itself as the jSketcher engine build and contains OCCT-derived source and build scripts. The exact correspondence of its source/build inputs to the shipped npm binary has not yet been established by a clean rebuild. Public distribution remains gated pending a complete provenance and license review.

To repeat the local tests, build with `npm run build`, build the test helper with `./node_modules/.bin/webpack --config test/webos/webpack.config.cjs`, serve `dist` on loopback, and run `test/webos/storage-isolation.test.cjs`, `test/webos/snapshot-workflow.test.cjs` and `test/webos/file-actions.test.cjs` with `puppeteer-core` available and a Chrome DevTools endpoint. `CODI_PHONE=1` selects the emulated-phone viewport. Generated bundles and dependencies are not source artifacts. `npm run check-code` currently fails on the pre-existing `web/app/cad/sandbox.ts` TypeScript error concerning `visual`; the application build and the specified browser tests passed.

A focused run of five upstream craft cases was made with the accidental `only` selectors removed and the asynchronous setup timeout increased from 4 to 60 seconds. The plane case passed; extrusion and cut cases raised `Cannot read property 'near' of null` during test-simulated ray picking, revolve timed out, and boolean intersection raised an undefined-value error. This is not a full-suite pass, and these results do not establish whether each problem is in the harness or the interactive application. The baseline app's `customRaycast` constructs a Three.js raycaster without assigning its camera; testing a possible fix is in progress. The separate Chromium rectangle-extrusion/reload/history smoke check described above did pass.

A temporary experiment assigned the current camera to that raycaster. It avoided the original null-camera exception, but the two focused extrusion and cut cases then timed out at 60 seconds. The experiment has not been adopted; further investigation is needed.

Follow-up: a Chromium trace identified the second Extrude wizard's missing face after the sketch closes. With the camera assignment and an explicit re-selection of that face in the COI1 extrusion test, Chromium completed the second extrusion and showed three history operations and two solids. The focused upstream Cypress case then passed with assertions for that history and model count, using the temporary runner's 60-second setup timeout. This does not establish that the other extrusion, cut, revolve or boolean cases pass; the temporary broad run had failures described above.
